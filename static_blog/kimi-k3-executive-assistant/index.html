B.02 AI, deployed

Kimi K3 and an agent harness: an AI chief of staff for your leadership team

Moonshot’s open-weight Kimi K3 is the brain. An agent harness is what turns it into an assistant that drafts memos, triages a calendar, and knows which actions need a human’s yes first — all on hardware your company controls.

By ICE Castle Infrastructure Team/OCT 16, 2026/6 MIN READ

An open-weight model is just a brain in a jar until something gives it hands. Moonshot AI’s new Kimi K3 is the biggest open brain released so far. An agent harness — the software layer that lets a model read a calendar, pull a file, draft a reply, and know which of those it isn’t allowed to do alone — is what turns it into an assistant your leadership team can actually use. Both halves can run on hardware you control.

01 / WHAT KIMI K3 IS

On July 27, 2026, Moonshot AI published the full weights for Kimi K3 on Hugging Face, alongside a technical report and three training-infrastructure tools (MoonEP, FlashKDA, AgentEnv). At 2.8 trillion total parameters it is, by Moonshot’s account, the largest open-weight model released to date, under a modified MIT license that permits commercial use, fine-tuning and local deployment. It is a mixture-of-experts model with a one-million-token context window and native image understanding, and it is also available hosted through Kimi Code, the Kimi app and Kimi API — but the open weights mean you don’t have to use any of those.

2.8T params, 1 license
Kimi K3 ships under a modified MIT license that permits commercial use, fine-tuning and self-hosting — the open weights, not a hosted API, are what make a private deployment possible.*

Moonshot’s own benchmarks put K3 ahead of every other open model and most closed ones. Independent analysis is more measured: Artificial Analysis places it around the level of Claude Opus 4.8 and GPT-5.5, behind the newest closed frontier models. That is still a remarkable result for an open model — and more than enough brain for the work most executives actually delegate.

02 / THE MODEL IS NOT THE ASSISTANT

A raw model answers questions. An assistant reads your calendar, drafts the reply, checks a number against last quarter’s board deck, and asks before it sends anything external. The layer that adds those abilities is what Google Cloud calls an agent harness: software that surrounds a model and gives it tool access, memory across sessions, multi-step execution, and — critically — permission checks before it acts. The harness is also where you draw the line between what an assistant can do on its own and what it has to ask a human for first.

This matters because harness and model are two separate decisions. Point an open harness — Google’s Agent2Agent protocol, LangGraph, CrewAI, or one your team builds — at an OpenAI-compatible endpoint you run yourself, and you can swap Kimi K3 for whatever model leads next quarter without touching the permission logic, the tool wiring, or the audit trail you already built. That is the real advantage of open weights: not just cost, but not being locked to one vendor’s model and one vendor’s agent platform at the same time.

03 / WHAT IT TAKES TO HOST IT

Kimi K3’s size is the headline, and it is also the sizing problem. At FP8 — the precision most providers use to serve a model this large in production — the weights take roughly 2.8TB of memory. A single 8×B200 node has about 1.5TB of HBM, so two nodes comfortably hold the full set of experts with headroom for the key-value cache a one-million-token context window needs. Run it at full FP16 instead and that doubles to roughly 5.6TB, which pushes you to four nodes. Mixture-of-experts routing means the model only computes with a fraction of its parameters per token — independent estimates put that at around 104B active parameters across 16 of 896 experts — but every expert still has to sit in memory somewhere, because any token can route to any of them.

2.8TB (FP8) / 5.6TB (FP16)
Memory Kimi K3’s weights need at each precision. Two 8×B200 nodes cover the FP8 deployment; four cover full precision.*

If your team is leaning on the full one-million-token context for things like multi-year contract review or a decade of board minutes, read when the B300 is worth the upgrade before you commit to a node count.

04 / WHAT IT COSTS FOR A LEADERSHIP TEAM

Take a two-node FP8 deployment — 16 GPUs — serving a 50-person leadership team: the CEO’s staff, function heads, and the people who prep board materials. The lease on 16 GPUs at our ~$5/GPU-hour target for qualifying 36-month commitments runs about $58,400 a month. Add a flat $5,000 for support and amortize a $20,000 setup fee (model serving, SSO, the tool integrations your harness needs) over the term, and the bill lands around $63,960 a month.

~$1,280 / person / month
$58,400 GPU lease + $5,000 support + amortized setup, spread across a 50-person leadership team. Half as many seats as our GLM-Legal example sharing the same 16 GPUs roughly doubles the per-seat cost.*

That per-seat number is higher than it would be for a larger group sharing the same two nodes — the baseload economics are the same whether 50 people use it or 200, only the denominator changes. The number that matters is usage, not seats: a model running on your own nodes has no per-token meter, so an executive assistant drafting board materials at midnight before a filing deadline costs the same as one that sits idle most of the week. For a leadership team, the question isn’t whether 50 people can justify two GPU nodes on a seat-by-seat basis — it’s whether faster board prep, cleaner diligence memos, and fewer hours spent hunting for a number in last year’s deck are worth it. For most companies that already pay this group’s salaries, the answer comes quickly.

05 / HOW TO GET STARTED

Start with two or three workflows where the harness’s permission checks do real work: calendar and inbox triage that drafts but never sends, meeting-prep briefs that pull from your CRM and prior board decks, and financial-model sanity checks that flag a number instead of changing one. Keep a human approving anything that leaves the building — an email, a filing, a wire instruction — and let the harness enforce that boundary instead of trusting the model to remember it. Executive communications, cap tables and HR matters are exactly the material most companies don’t want flowing through a third-party agent platform’s logs; running the model and the harness on infrastructure you control is what keeps that material inside your own boundary. When you request a quote, tell us your headcount, context-length needs and which tools your harness has to reach, and we’ll size the deployment honestly — including telling you if two nodes is overkill.

The model is the part everyone talks about. The harness and the hardware are the parts that decide whether your leadership team’s actual work — and its actual secrets — stay on infrastructure you control.
